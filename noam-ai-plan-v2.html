01 · Positioning

The open lane is empty

Two axes decide this market: how well a tool does real-time collaboration, and how open its AI story is (bring your own key, harness, and model, with scoped permissions). Everyone clusters in three corners. Nobody owns the fourth. One clock is ticking: a public obsidian-multiplayer spec explicitly targets "the obvious self-hosted solution for enterprises with real IT requirements." That is this lane, described in someone else's roadmap.

Guardrail

Notion drift test

Every feature must answer: does this work on plain .md files I control? Block databases, wikis-as-product, and per-seat rent fail the test on sight.

Moat

What competitors can't copy cheaply

The Rust bridge (Markdown to CRDT) plus the permission engine that evaluates before data moves. Presence, diffs, and agents all ride on these two. The audit also found a third: a shipped MCP server and ACL most plans would still be designing.

Boundary

What you never maintain

Inference bills, API keys server-side, agent implementations, a plugin registry, a hosted playground. BYOK plus community-owned vault files keep the maintenance surface yours. Agents are file-only through Noam: harnesses bring their own shells, and that is stated loudly, not hidden.

03 · Architecture decision record

Four decisions gate everything

The eng review refused to greenlight Phase 2 or 3 code until these are recorded. Each ADR below carries options, a recommendation, and what happens if you pick otherwise. Status on all four: proposed, awaiting John's call. Nothing here is irreversible except deferring E2E encryption, which is flagged where it bites.

ADR-1 · Proposed · gates Phase 2

Suggest-mode staging semantics in Yjs

Yjs has no "proposal" concept. "One linear suggest/accept loop" contradicts CRDT concurrency: two overlapping proposals need a defined conflict rule, and reject must compute inverses across concurrent edits. Pick the primitive before a line of Phase 2 code.

OptionHow it worksTradeoff
A. Sandbox Y.Doc per proposal (recommended)Each proposal lives in its own Y.Doc branched from the note. Accept replays its ops onto the live doc; reject drops the doc. If the base region changed underneath, accept raises a conflict card instead of merging.Cleanest conflict semantics, heaviest primitive. Merge-time conflict UI must be designed (it is, in section 05).
B. Op-metadata flagsProposals are ops in the shared doc flagged as unaccepted, hidden by the renderer.Lighter, but proposal state pollutes the shared doc and syncs to clients that do not understand the flag.
C. Apply-and-undoApply the edit, keep the inverse, undo on reject.Simplest, but reject-after-concurrent-edits can clobber. Unsafe under real collaboration.

Recommendation: A. It is the only option where "reject" is always safe and "accept" has a defined conflict moment. Cost: the conflict card at merge time, which section 05 designs.

ADR-2 · Proposed · gates Phase 3

Local-write enforcement point for BYOH

A BYOH harness (Claude Code, Codex CLI) pointed at a personal vault's local files writes through the OS. The Rust bridge egests via filesystem watch. Nothing evaluates a scope grant on that path, so "scoped permissions" are advisory there unless something changes.

OptionHow it worksTradeoff
A. Gated local socket + honest flagging (recommended)Agent writes to vault files go through the bundled local MCP socket (stdio transport). The filesystem watch detects writes that bypassed the socket and marks them unmediated in the audit log, visible in the timeline.Real mediation on the happy path, honest labeling off it. Requires the socket to be the documented and easiest path, or nobody uses it.
B. Noam spawns and sandboxes the harnessNoam launches the agent process itself inside an OS sandbox with the vault mounted read/write per the grant.Strongest guarantee, biggest scope. A process manager is a new product surface.
C. Audit-only for local vaultsDeclare local-vault agent access unmediated by design; permissions apply only to the server path.Honest, but guts the trust story for personal vaults, which is where most agents will run first.

Recommendation: A. It keeps the trust story true on the path you control and labels the path you do not, instead of pretending. The MCP socket also needs loopback-plus-token auth, or the permission engine is theater on every path.

ADR-3 · Proposed · gates Phase 3

Agent-scoped token kinds and registry location

MCP tokens today are scoped to (user, vault) and act as the user. That is user impersonation: every audit line and every error says "you" when the agent did it. The plan's reader/drafter/editor presets need a new token kind, and the registry needs a home.

DecisionRecommendation
Token kindNew agent-scoped token kind carrying (agent participant id, vault, folder/file scopes, approval mode). Minted from the registry, revocable per agent, and every error and audit line carries the participant id.
Registry locationServer-side Postgres, next to vaults/folders/notes. Team presence cannot work from a per-vault file. Builder-visible state is documented once, in the tool reference.
Agent display identityRegistry-signed. No agent named "John". Display names render from the registry row, never from agent-supplied strings.
Read instrumentationLog reads, not just writes. read_note / search_notes log token id, doc id, timestamp. Without this, the prompt-injection mitigation is theater.
ADR-4 · Proposed · gates Phase 4

Who runs the jobs

No scheduler exists anywhere: not in the Tauri desktop, not on the server. A morning digest needs a cron owner, and "jobs as vault files" needs someone to wake up and run them.

OptionHow it worksTradeoff
A. Desktop scheduler for personal, server cron for team (recommended)Tauri-side scheduler runs vault-file jobs for personal vaults; the sync server runs them for team spaces.Two implementations, but each is small and each matches where the vault lives.
B. Desktop onlyJobs run only when your machine is awake.Simple, but team-space jobs silently stop when laptops close.
C. Server onlyPersonal vaults need the sync server to get jobs.Couples a local-first product to a server for its headline feature.

Recommendation: A. And Phase 4 is cut to one reference job (morning digest) until the scheduler proves itself. Jobs produce diffs, never silent writes; job failure is loud, never a partial apply.

Phase 0 · Proposed prerequisite · gates Phase 1

Identity and team membership

Presence, attribution, permission badges, and "visible to everyone in the team space" all assume you know who everyone is. The plan had no identity story. Phase 1 without Phase 0 is a demo, not a product.

Recommendation: piggyback, don't build. Team spaces ride existing identity (Tailscale identity for the self-hosted lane) instead of a new auth system. One paragraph in the trust story, not a quarter of engineering. If team spaces ever need real SSO, that is a separate decision with a separate budget.

Flagged · needs John's call before any public launch

The revenue and messaging contradiction

Internal STATUS.md says per-vault Pro billing via Polar shipped (the Polar SDK is in the server, verified). Public messaging says free and self-hosted only, no managed tier. Both cannot be the story. Options: managed team-space hosting, per-vault Pro as the paid tier, or a compliance tier for the managed-device lane this product was born into. "Community-owned everything" is a growth strategy, not a business. Reconcile the two documents first, then pick one. No recommendation here: this is a founder call, not an architecture call.

04 · Phased plan

Five phases, each shippable alone

Order is deliberate: identity first because everything assumes it, presence second because everything hangs off it, diffs third because they are the trust mechanism, the agent socket fourth because it needs all three, and one reference job last because it needs the socket. Phase 1 is greenlit now. Phases 2 and 3 wait on the ADR.

Phase 0

Identity and team membership

The prerequisite. Small on purpose.
Ships: team spaces bound to existing identity (Tailscale identity in the self-hosted lane). A human is a participant row; a team space is a set of participant rows. Nothing more.
Not building: a Noam auth system, SSO, or device management. If those ever come, they are a separate decision with a separate budget.
Phase 1 · greenlit

Presence for humans

The visible foundation. No AI yet. Mostly UI over existing infra.
Ships: participant registry schema with kind in {human, agent} from day one, so Phase 3 adds rows, not migrations. Toggleable right sidebar: Online now, Agents active, In this note. Live cursors already ship (animated carets with name flags); Phase 1 gives them registry colors. Per-note presence chips. Heartbeat every 10s; cursor fades after 30s without one, removed after 90s with a quiet panel note. Stale presence is loud, never a ghost. Desktop-only declared explicitly for Phase 1; mobile responsive lands in 1.x.
Not building: follow mode (deferred to 1.1, viewport sync is the expensive piece), comments, @mentions, notifications. Agent identity colors are defined now anyway: a fixed 8-color colorblind-safe palette designed for Noam (no reds or oranges, violet reserved for Noam's own actions), never colliding with text-selection color. Retrofitting this later would break muscle memory.
Phase 2 · needs ADR-1 sign-off

Diffs as the interaction model

The trust mechanism. Still no AI. The riskiest build in the plan.
Ships: suggest mode for all edits (propose to accept or reject), built on the ADR-1 sandbox-doc primitive. Op-coalescing rules: keystrokes coalesce per paragraph within a 2s window, a proposal is a set of coalesced regions, 47 keystrokes are never 47 diffs. Per-note history timeline from the op log with a retention SLO: op-level detail 90 days, snapshots beyond, timeline query under 200ms on a year-old note, measured on a real 10k-note vault as a Phase 2 acceptance criterion. "What changed while you were away" digest. The full interaction spec is section 05.
Not building: branching, PR-style review flows. Git stays the power tool underneath. Do not start Phase 2 code until ADR-1 is signed.
Phase 3 · needs ADR-2 and ADR-3 sign-off

Agent participant protocol

The socket. Smaller than v1 implied: the transport is shipped, the surface is not.
Ships: agent rows in the registry, agent presence chips with visible permission badges, agent-scoped token kinds (ADR-3), MCP socket with loopback-plus-token auth, setup wizard ending in noam agent verify (section 06), error contract and noam agent lint, AGENTS.md schema and starter template, noam workflow dry-run, per-agent approval modes with always-ask default plus the fatigue answer (batch review, per-agent and per-note trust tiers). Tools default to read-only scopes; every agent mutation returns a suggestion id. Harness setup paths for Claude Code, Codex CLI, and Gemini CLI. BYOK in the system keychain, MCP tokens server-minted and shown separately (section 07).
Not building: a Noam model, hosted inference, a model gallery, server-side key storage, shell execution through Noam (agents are file-only; harnesses bring their own shells, stated loudly), a hosted playground, multi-language SDKs, a workflow package manager. Split suggestion from v1 stands: registry plus presence chips first, MCP tools second.
Phase 4 · needs ADR-4 sign-off · cut to one

One reference job as a vault file

Sell outcomes, not "AI". One exemplary file beats three mediocre ones.
Ships: the morning digest as a vault file: what changed, rendered as diffs, written in a teammate's voice, not a changelog. Passes noam agent lint and noam workflow dry-run in CI. Starter template repo with one-click fork and a lint action. Folder convention plus a README that renders somewhere users browse. Workflow files use YAML frontmatter plus markdown body, carry noam-agent: v1, and may include one other workflow file by vault-relative path (cycles rejected by lint). Exit criteria: lint plus dry-run green in CI, docs shipped with the file.
Not building: a marketplace, ratings, a hosted workflow runner, or the other two reference jobs yet. Let the gallery grow or not on its own. Interrupted agent work is explicitly out of scope for v1: pending proposals stay as pending diffs, no auto-resume. Named and cut, not forgotten.

05 · The diff loop, designed

Nobody builds Phase 2 by inventing this

The design review's core finding: the make-or-break interaction was a paragraph. This section is the spec. Rendering, keyboard, states, decay, conflicts, fatigue, accessibility, and the three authored moments that make it feel alive.

Rendering

Where diffs live

  • Inline in the editor with gutter markers, plus a persistent review bar: count, prev/next, accept, reject.
  • Approval requests live in the review bar. Never toasts. Toasts are for things you can ignore; approvals are the product.
  • Agent badges in three places: presence chip, settings row, inline next to that agent's diffs.
  • One principle: agents are teammates, so every place a human's name appears, an agent's name appears in the same slot.
Keyboard

The highest-frequency interaction

  • ] / [ move between suggestions, A accepts, R rejects.
  • Keys are hinted in the review bar itself. Five diffs clear without touching the mouse.
  • This grammar is a proposal for John's taste check. It cannot ship unspecified; the keys can change, the existence of keys cannot.
State tables

The states that will actually bite

StateRule
Stale presenceHeartbeat every 10s. Cursor fades after 30s silent, removed after 90s with a quiet panel note ("Claude disconnected mid-edit"). A ghost cursor is worse than no presence.
Diff conflictA human edit under a pending suggestion turns it into a conflict card showing both versions, side by side, with keep-mine / keep-theirs / keep-both. No silent merge, no silent clobber.
Grant revoked mid-sessionThe agent's presence chip retracts immediately, in-flight proposals freeze as pending, and the audit log records the revocation with a timestamp.
MCP server unreachableThe verify probe prints the attempted endpoint, the failure class (connection refused vs auth vs protocol), and the exact command to fix it. No spinner of doom.
Key add failureNames the keychain operation that failed and the OS permission to check. Keys are never retried silently.
Empty statesNo proposals: "Nothing to review. You are caught up." No agents: the existing copy stands ("Bring your own harness. Noam never sees your keys.").
Fatigue

The interaction answer to always-ask

Always-ask is the right default on day one and a click ritual by day thirty. Policy alone does not fix that; interaction does:

  • Batch review: clear a queue of low-risk proposals in one pass, each still individually visible.
  • Per-agent trust tiers: "always ask" per agent, relaxable to "auto-accept in drafts" or "auto-accept in this note."
  • "Accept all from Claude in this note": the pressure valve for long sessions.
  • Risk-tiered approvals underneath: low-risk proposals batch, high-risk ones interrupt. The audit log scores proposals, not just records them.
Access

Screen readers, touch, motion

  • Live cursors are aria-hidden with a polite text alternative ("Claude is editing paragraph 3"). Diffs announce linearized changes. Presence changes never spam live regions.
  • 44px minimum touch targets. The v1 mock's 40x22 switch is redrawn at 44x24 in section 07.
  • Reduced-motion path: follow mode and cursors use jump cuts, not smooth tracking.
  • Presence panel: toggleable right sidebar (Online now / Agents active / In this note), shortcut-toggleable, collapsed by default in personal vaults, on in team spaces.
Delight

Three authored moments

  • First-agent welcome: the first time an agent cursor appears, a small inline introduction states its scope in plain words. It should never feel like surveillance.
  • Accept celebration: a suggestion accepted feels crisp, one satisfying micro-transition, not a checkbox dying.
  • Digest voice: "while you were away" reads like a teammate's summary, not a changelog. This is the feature that justifies the product to a skeptic.
  • Reversibility copy, explicit: "Every accept is reversible for 30 days." Reversibility is the feature that lets people trust the scary part, so it gets a sentence, not a footnote.
Identity color

Agent palette, fixed before Phase 1

Eight agents with presence chips, cursors, and diff highlights need a fixed, colorblind-safe palette. The set below is a fixed 8-color colorblind-safe palette designed for Noam (no reds or oranges, violet reserved for Noam's own actions), assigned in registry order:

06 · Builder experience

The socket was a button. Now it has a flow.

The devex review's verdict: the MCP server already exists, so Phase 3's work is documentation and error quality, not construction. This section specs the wizard, the tool inventory, the error contract, and the exit criteria that make builders succeed. Target: 2 to 5 minutes from "Add agent participant" to a verified connection with the harness installed, 10 to 15 end to end.

Wizard

"Add agent participant", specified

  1. Pick harness: Claude Code, Codex CLI, Gemini CLI, or local. One screen, one choice.
  2. Config block: Noam shows the exact config snippet for that harness (copy-paste default; auto-write into the harness config is opt-in later, because it touches files outside the vault). Transport: stdio is primary, the harness-native pattern. One primary, documented.
  3. Scope the grant: folder picker plus the three preset roles (reader, drafter, editor), per-note override only when asked.
  4. Mint the token: agent-scoped token (ADR-3), shown once, stored where the harness expects it.
  5. Write AGENTS.md: generated from a real schema-backed template, then validated by noam agent lint before it is saved.
  6. Verify: noam agent verify calls tools/list over the bundled server and prints green: the agent's presence chip appears live in the panel. This is the magical moment, designed as the payoff: you watch "Claude is editing Q3 Planning" appear, then approve its first proposed diff from inside Noam.

Measured from day one of Phase 3: time from the "Add agent participant" click to verify-green, plus drop-off per wizard step. One recorded fresh-machine friction audit before Phase 3 sign-off.

Tool inventory

The 15 tools, published

Verified in the repo at POST /api/mcp: all 15 tools, listed here: list_vaults, list_folders, list_notes, read_note, search_notes, query_knowledge, create_note, update_note, append_note, edit_note, delete_note, create_folder, delete_folder, move_note, move_folder. The plan appendix (a Phase 3 deliverable) publishes all 15 with names, parameters, defaults, and scope requirements. Rules:

  • Tools default to read-only scopes; write grants are explicit.
  • Every agent mutation returns a suggestion id the UI can render. No silent applies.
  • Errors carry the participant id, so the message names the agent, not "you."
  • Naming grammar is guessable (noam.read_note style) and tools/list reads clean without the docs open.
Error contract

What happened, why, how to fix

Every error follows the formula: what happened, why, how to fix, where to learn more, the actual values. The three paths that must ship with before/after message text:

  • Permission denied (the most common event in a scoped system): structured error with the denied path, the scope the agent holds, the grant it needs, plus a user-side one-click "approve this scope" affordance.
  • Malformed AGENTS.md or workflow file: noam agent lint with Elm-style output: file, line, what was expected, the fix.
  • Harness cannot reach the server: the probe prints the attempted endpoint, the failure class (connection refused vs auth vs protocol), and the exact command to fix it.
  • Plus a debug/verbose mode for the MCP server. Every error links to its docs page.
Authoring

Files you can trust

  • AGENTS.md schema plus starter template plus validator. The most-copied artifact in the Tolaria pattern is currently a string in a plan; it becomes a real file with a real schema.
  • Workflow format: YAML frontmatter plus markdown body, carrying noam-agent: v1. Parseable, versionable, familiar.
  • noam workflow dry-run <file> renders the proposed diffs without applying anything. Authors iterate safely. CI-usable non-interactive mode for lint.
  • Versioning: the registry pins the protocol version per agent. Renames ship with in-app deprecation warnings one release before removal. noam workflow migrate rewrites files forward. One paragraph in the architecture, multi-year consequences.
  • Offline-first, stated: everything here works with the network off. That is a selling point, say it.
Docs

Exit criteria, not aspirations

Docs ship with the feature or the feature does not ship. Phase 3 is not done until all five exist:

  • Quickstart: copy-paste to a verified connection in under 5 minutes, with real shown output.
  • Tool reference: one real example per tool.
  • AGENTS.md authoring guide and workflow-file authoring guide.
  • Error catalog, with every message linking back.
  • Docs versioned with the app, so v0.2's protocol docs never describe v0.1's tools.

08 · Decisions & risks, updated

What needs your call

D1 · Default approval mode

Proposal: "always ask" stays the default, with the fatigue answer built in from day one: batch review, per-agent and per-note trust tiers, "accept all from Claude in this note." Rationale: trust is the pitch, but a default that becomes a click ritual by week two is a security hole, not a UX nicety.

D2 · Agent visibility

Proposal: agent presence is visible to everyone in the team space, with its permission badge. No invisible agents. Rationale: invisible automation is how trust dies. This is a privacy call worth making deliberately, not by default.

D3 · Sequencing vs E2E encryption

Proposal: ship presence and diffs before end-to-end encrypted sync, and say plainly in the trust story that the server sees presence and note titles until E2E lands. Rationale: E2E complicates the presence channel and server-side digests; get the interaction model right first on trusted servers. Hard-to-reverse call, flagged as such.

D4 · Human suggest mode

Proposal: human collaborators get suggest/accept/reject too, on by default in team spaces. Rationale: one interaction model for all edits is the plan's thesis; it should apply to people, not just agents.

D5 · Mobile scope

Proposal: Phase 1 is desktop-only, declared explicitly. The presence panel and review bar get a real mobile design in 1.x. Rationale: desktop assumptions calcify into layout; better to declare the boundary than ship a stranded mock.

R1 · Prompt injection via vault, modeled

An agent reading a malicious note can be steered by its contents. Mitigations, all specified now: scope grants plus always-ask diffs bound the blast radius to one proposed edit; the audit log instruments reads (token id, doc id, timestamp), not just writes; agent display identity is registry-signed, so no agent can wear your name; exfiltration is named as an open problem, because the permission engine governs what agents touch, not what a networked agent sends home.

R2 · Permission UX complexity

Per-file grants can become a chore. Mitigation: folder-level defaults, three preset roles (reader / drafter / editor), per-note override only when asked, and a denial UX that names the fix instead of a dead end.

R3 · History storage growth, with a number

CRDT op logs grow with every keystroke. Mitigation: snapshot plus compact already ships server-side (50-update threshold). v2 adds the SLO: op-level detail 90 days, snapshots beyond, timeline query under 200ms on a year-old note, measured on a real 10k-note vault as a Phase 2 acceptance criterion, not a footnote.

R4 · Notion drift

Guardrail from section 01: every feature must work on plain .md files the user controls. Block databases and per-seat rent on sight. Unchanged, still load-bearing.

R5 · Bulk-write reindex bottleneck

New from the audit: MCP writes trigger reindex, so an agent doing bulk append_note loops could make FTS reindex the bottleneck. Mitigation: a bulk-write benchmark is a Phase 3 acceptance criterion.

10 · Recommendation

Greenlight Phase 1. Decide the ADR. Then build.

The tuned call

Start with Phase 0 + 1, decide the ADR, then Phase 2

Presence and diffs are valuable for human teams with zero AI involved, and they are the foundation the agent socket needs. Phase 1 is mostly UI over shipped infra, so it can start now, with the participant registry built right the first time (agent kinds included). Nothing in Phase 2 or 3 starts until the four ADRs are signed, because the staging primitive, the enforcement point, the token kinds, and the scheduler are load-bearing for everything above them. Phase 4 stays one reference job until the scheduler proves itself. The empty quadrant has a clock; this sequencing is the fastest honest path into it.

Kept

  • The participant registry: one table for humans and agents
  • Phases 1+2 before agents: presence and diffs first
  • Diffs as the interaction model, not chat
  • Boundary discipline: no inference bills, no server-side keys
  • Forkable vault files, no central registry, gists as distribution
